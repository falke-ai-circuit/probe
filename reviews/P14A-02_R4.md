## 1. Digest read from the registry (research leg)

Docker daemon is not reachable from this host (`Cannot connect to the Docker daemon at
unix:///var/run/docker.sock`), but `docker manifest inspect` and the registry HTTP API both work
without one — the registry is the authority here, so the digest is **read**, not copied from the
P16-01 log.


It agrees with the publishing workflow's own record (`.github/workflows/docker.yml:88` builds
`platforms: linux/amd64,linux/arm64`; `:100-107` records the digest and the platform line), and with the
P16-01 log line `exporting manifest list sha256:1051de24…` — but the value in the tree comes from the
registry response above.

**Why the tag changes with the digest.** Every published tag in the registry (5 total: `9d2be637…`,
`54ed5316…`, `8a44426b…`, `70de7fa…`, `e46023f…`) was inspected: the four older ones are
`amd64 + attestation` only, and `70de7fa` resolves to `sha256:466b2fc2…` — the digest the repo pinned.
The only multiarch index published is `e46023f1cd07…@sha256:1051de24…`, so naming that digest means
naming that commit tag. Tag and digest therefore still describe the same manifest, which is the point of
the pin discipline; they are simply a newer pair than `70de7fa@466b2fc2`.

## 5. Open item

ahead of the `70de7fa` release commit (the P10–P13 units landed between them) while
