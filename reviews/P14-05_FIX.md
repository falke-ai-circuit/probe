## R1 — PointIn decoded the reply four bytes early

`internal/agent/x11_point.go:41-46` now reads the `TranslateCoordinates` reply at its declared offsets:

```go
child := binary.LittleEndian.Uint32(reply[8:12])
dx := int32(int16(binary.LittleEndian.Uint16(reply[12:14])))
dy := int32(int16(binary.LittleEndian.Uint16(reply[14:16])))
```

previously `child` came from `reply[4:8]` — the reply's **length** word, always 0 for this reply — and
`dx`/`dy` from the child word (`reply[8:10]`/`[10:12]`). Same offsets as `translateToRoot`
(`x11.go:262-274`); each site keeps its own read because one asks root→window and the other
window→root, and only the field offsets are shared (comment added naming the layout).

## R2 — the shared read path now consumes the reply's whole tail

`x11Conn.do` (`x11.go:222-256`) reads the 32-byte header, then drains `4*length` bytes
(`reply[4:8]`, in 4-byte units) and returns header+tail as one slice. That is the single place a
reply is read, so no future fixed-size caller can leave bytes on the connection. Error packets are
returned before the length word is interpreted (an error's [4:8] is the bad resource, not a length);
an implausible length (> 1 MiB) is an error, not an allocation.

`property()` (`x11.go:288-331`) previously read its own tail off the wire; it now slices the drained
tail at `reply[32:32+need]`, with a short-tail error instead of a blocking read.

`attributes` needed no per-call change: `GetWindowAttributes` (44 bytes, length word 3 → 12 tail
bytes) is correct by construction once the drain is in `do()`. The P14-04 fix list suggested a local
drain in `attributes`; the brief required one drain in the shared read path, so the drain lives in
`do()` and `property` was moved onto it — a local drain plus a `do()` drain would double-read.

Requests with no reply stay off `do()`: `RequestForeground` and the XTEST event writes advance the
sequence by hand, as before.
