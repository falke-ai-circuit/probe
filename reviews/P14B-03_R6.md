## 3. The fix (the mapper answers, nobody re-scans)

`planText` now returns a typed `*codepointFailure` — the rune and its index in the string, or `at: -1` when the failure belongs to no rune:

```go
type codepointFailure struct {
	r   rune
	at  int
	why error
}
```

- Rune-level branches (control char with no keysym, lone surrogate, out of range) carry `r` and its index — the same rune they always named, now with a position.
- The keycode-range branch names the **first rune above UCS-2**, because that is the rune a borrowed keycode would have had to hold, and §9.4's carriage rule is "astral planes **where the keycode range allows**" (`P10-07_CONTRACT_V3_1.md:563`). A string whose runes are all carryable has no such rune: the failure is the borrow, and the failure carries `at: -1`.
- Invalid UTF-8 refuses before the rune loop and stays a plain error — no rune was decoded, so none is named.

`codepointUnsupported(env, why error)` reads the typed error via `errors.As` and adds `codepoint` + `index` **only when `identified()`**:

```go
var cf *codepointFailure
if errors.As(why, &cf) && cf.identified() {
	detail["codepoint"] = fmt.Sprintf("U+%04X", cf.r)
	detail["index"] = cf.at
}
```

Both call sites pass the failure itself (`agent.go:1246` `perr`; `:1252` `&codepointFailure{at: -1, why: terr}` for the post-plan keystroke path). Neither call site re-derives anything from `params.Text`.
