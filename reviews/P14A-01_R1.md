# P14A-01 — R1: an undelivered write must not report "update in progress"

**Unit:** P14A-01 · **Commit:** `e159de3` (branch `r119-build`, pushed, tree clean)
**Defect:** P12-06 residual R1 — `internal/server/server_api.go:885-888` returned a bare error when
`conn.WriteJSON(env)` failed; `handleAgentUpdate` (`internal/server/server_update.go:290-296`) read any
non-`ForwardRefusal` error as "written, the answer did not arrive before the deadline" and answered
HTTP 200 `{"status":"update_in_progress"}` for a command that never reached the agent.

## 1. What changed

| Site at `e159de3` | Change |
|---|---|
| `server_api.go:787-795` | third member added to the closed refusal enum: `RefusalDeliveryFailed = "DELIVERY_FAILED"` |
| `server_api.go:901-913` | write failure returns `*ForwardRefusal{Code: RefusalDeliveryFailed, AgentID, Message, Err}` instead of `fmt.Errorf("send to agent failed: %w", ...)` |
| `server_update.go:276-279` | `case RefusalDeliveryFailed: status = http.StatusBadGateway` (409 stays the default for any future code) |
| `server_api.go:917-932` | audit row for an agent-side typed error: `"success"`/`""` → `"error"`/`Code+": "+Message` |

**Why a new code and not an existing one.** The enum held two states, and neither describes this one:
`AGENT_NOT_CONNECTED` is false (there is a live connection in `s.conns`, and `s.connWriteMu` has an
entry — both pre-send checks passed), `CAPABILITY_MISSING` is false (the registry advertises `update`).
The command nevertheless never left the server, so it is a refusal in the caller's terms. `DELIVERY_FAILED`
is that third state, and the route's switch is exhaustive over the enum, so no code silently falls to the
409 default. 502 is chosen because the request was valid and the failure is on the link to the agent —
the upstream — not in the request (403/409/503 keep their existing meanings; the P9-01 status table gains
one row, which is flagged for review in §5).

**Error identity is preserved:** `Err` is the original transport error and `ForwardRefusal.Unwrap` returns
it, so `errors.Is/As` against the underlying write error still work. No caller matches on the old
`"send to agent failed"` string (the only site that produced it is the one changed; `tunnel.go:188` logs
its own).

## 2. Item 2 — the audit line: fixed, not justified

`:899` logged `result:"success", error_msg:""` when the payload carried `resp.Error` (the agent answered
with a typed error). That is **not** the delivery lie of R1 — the frame demonstrably reached the agent,
which is why a reply exists at all — but `"success"` is the audit's own word for the action succeeding
(`audit.go:20`: `"success", "denied", "error"`), and the command did not succeed. It recorded a success
row for a failed action, which is the same false-success shape one layer down. The row now says
`"error"` with the agent's code in `error_msg`; delivery remains implicit in the presence of an
agent-side code. Nothing in the tree consumes the old value (grep: no assertion or metric reads
`Result=="success"` for a typed agent error), so this is a correctness change, not a behaviour break.

The undelivered path was already honest at this site: the write-failure branch logs `"error"` with
`"send to agent failed: ..."` before returning, and the new typed return does not alter that row.

## 5. Scope, and what this unit did not do

- **R2 untouched.** The refusal branch's side effects (`markArtifactInFlight`/`setUpdateArtifact`/
  `registerArtifact` above the send, `purgeCanaryRegistryRow` at `server_update.go:243`) still run before
  the write is attempted, so a *delivery* refusal reaches the same branch as a capability refusal and
  still pins the artifact and purges the canary row while the comment says "Nothing was staged". This
  unit makes that branch reachable in one more case; it does not change what the branch does. R2 remains
  open for its own unit.
- Update state machine, canary logic, §9/§10, deploy path: untouched. No signature changed; the new
  error is the same type the route already handled, so no other handler's behaviour moves (every other
  `forwardToAgent*` caller already returned its error to the caller as a 5xx).
- **Flagged for the review leg:** a new status row (502 `DELIVERY_FAILED`) on the update route. It is
  not in the P9-01 contract's status table — recorded here rather than edited into the contract, since
  contract text is the architect's.
