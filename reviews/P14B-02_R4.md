## 0. Decision: LABEL, not refuse

The contract line relied on, verbatim (`docs/contracts/P10-07_CONTRACT_V3_1.md:566`, §9.4):

> `encoding:"utf16"` means the caller supplies code units and probe must **not** re-encode: on Windows it emits
> them verbatim; elsewhere it decodes to UTF-8 first and reports `detail.transcoded:true`. Never silently lossy.

Two sentences of justification: the contract's only stated requirement for this class is *"Never silently
lossy"*, it already licenses reporting through `detail` (`transcoded`), and it nowhere authorises refusing a
string it can type — so the permitted mechanism is a report, not a refusal. Refusing would also destroy valid
input: a caller who means U+FFFD and a caller who pasted half a pair cannot be told apart at that point, and
the contract's own answer to a typeable string is to type it and say what was done.

## 1. Where the loss actually happens (measured before the fix)

`encoding/json` repairs the code unit during decode, not during emission. Both bodies below succeed and
produce the same Go string, so no amount of looking at `params.Text` can tell them apart:

```
standalone: err=<nil> s="a\ufffdb" bytes=61efbfbd62
fffd:       err=<nil> s="a\ufffdb" equal=true
```

It is worse one layer up: `handleV1TextInput` decoded the body and forwarded the *struct*, so the escape was
destroyed before the agent existed. Probe run against the real parse+forward path
(`protocol.ParseStrictBytes[protocol.InputParams]` then `json.Marshal`):

```
body={"context":"x11::0","window":"0x3c00007","text":"a\ud800b"} serr=<nil> text="a\ufffdb" runes=[61 fffd 62]
  forwarded params={"text":"a\ufffdb","window":"0x3c00007","context":"x11::0"}
body={"context":"x11::0","window":"0x3c00007","text":"a\ufffdb"} serr=<nil> text="a\ufffdb" runes=[61 fffd 62]
  forwarded params={"text":"a\ufffdb","window":"0x3c00007","context":"x11::0"}
```

That measurement is what forced the server-side change in §5: a detector inside the agent alone would have
been correct and unreachable through the documented route.

## 2. Mechanism — seeing the surrogate before `encoding/json` replaces it

Raw `\u` scan over `env.Params`, which is `json.RawMessage` and therefore still carries the caller's bytes
(`protocol.Envelope.Params`). Three functions in `input_pointer.go`:

| function | job |
|---|---|
| `rawStringField` | `json.NewDecoder` + `Decode(&json.RawMessage)` — RawMessage **copies the value bytes without decoding them**, so the literal for `text` keeps its escapes |
| `jsonStringUnits` | walks that literal into UTF-16 **code units** with no repair: `\uXXXX` → the unit it spells (surrogates included), named escapes → their ASCII unit, literal UTF-8 → `utf16.Encode` of the rune |
| `unpairedSurrogates` | the decoder's own rule, applied to the units: a high surrogate not followed by a low one, or a low with no high before it, is one repair; a well-formed pair is consumed as two units and reports nothing |

`textDetail(env, enc, codePoints)` builds §9.4's `detail` in one place and adds `repaired_rune_count` +
`repaired_at` (1-based code-unit positions, the offsets the caller's own body shows) only when the list is
non-empty. The text that is typed is unchanged — this is a detector, not a second decoder.

## 7. Open item

`R4b` (same class, not covered): a body whose `text` contains **invalid UTF-8 bytes** is also repaired to
U+FFFD by `encoding/json`, and this detector answers "no repair" for it — `jsonStringUnits` reports code-unit
positions only, and a byte-level replacement has no code-unit position to name. Distinct from R4: R4 was an
unpaired *code unit*, R4b is an invalid *byte sequence*. Reporting it needs a second position space (byte
offsets) and a second key, so it is named here rather than silently absorbed.
