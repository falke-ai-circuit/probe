## 1. Decision: arm-then-commit

The purge moved **after** the frame write (`server_update.go:319`, formerly `:244`), so a forward that refuses
mutates no registry row. The justification is that the purge's own comment already described it as a
*consequence* of a start ("an update start supersedes any canary row left behind by an earlier attempt"), not a
precondition for sending: nothing between the old `:244` and the forward reads the registry row, and the only
consumer of "the canary row is gone" is the promotion/completion path, which by definition runs after the agent
received the frame. Keeping it before the write bought nothing and made the refusal branch's comment false. The
half that genuinely must precede the write is the artifact pin, and that is now an explicit arm that a refusal
disarms (see §2) rather than an undetectable leak.

The refusal branch no longer says "nothing was staged". It states what is true: no purge ran
(`detail.canary_row_purged: false`), nothing was delivered (`detail.delivered: false`), and the deliverable that
*is* now in the managed directory is named (`detail.staged_artifact: <abs path>`, empty in `ws_remote_path` mode
where the server stages nothing).

## Open item

The run at `e159de3` and this one both leave the **staged artifact and its ledger row** behind on a refusal. That
is now declared, not denied, but it is still a caller-visible residue: a refused update leaves the file in the
managed dir to age out under retention. Rolling it back would mean deleting a file the caller may have asked to
be there (`binary_path` semantics), so it is left as a declared residue rather than a purge — a product decision
for the owner if refusal should also unstage.
